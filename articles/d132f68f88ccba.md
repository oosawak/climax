# 🌀 序章：失われる記憶の呪い

AI と共に創造を進める者たちは、しばしば同じ悩みに囚われる。

- どの儀式（セッション）で何を行ったのか  
- どの精霊（AI）が何を語ったのか  
- どの工程が終わり、何が残っているのか  
- どの世界（プロジェクト）にどんな進捗があるのか  

これらは “記憶の霧” に飲まれ、やがて消えてしまう。

Climax の詠唱者であるあなたもまた、  
この **“記憶の呪い”** に悩まされていた。

---

# 🌌 第一章：Azure ― 蒼穹の記憶庫を得た詠唱環境

そこで現れたのが **Azure（蒼穹の記憶庫）** である。

Azure は、現世の神殿（Ubuntu）で行われる儀式（tmux セッション）を  
**蒼穹へと記録し、永続化する力**を持つ。

- Chrono Chamber（tmux）の構造  
- 精霊（AI CLI / LLM）の発言ログ  
- プロジェクトごとの進捗  
- 複数の神殿（サーバー）からの記録  
- GitHub（蒼穹の写本庫）との連携  

これらすべてを **Azure Functions（記録の使い魔）** と  
**Cosmos DB（記憶の書庫）** が受け止める。

---

# 目的（ざっくり）

- tmux の「儀式（セッション）」を保持し、後で取り出せるようにする
- セッション情報・ログを Azure Functions へ送って Cosmos DB に蓄積する
- Azure の NLPを使って、ログのタイトルなどの要約や翻訳をする。
- Azure の NLPを使って、intent / entities を抽出し、 英語の `english_prompt` を組み立て、日本語回答を強制した `final_prompt` を作成する。


# 何をする仕組みか

Climax Chronicle は次の2つを扱う。

- **セッション管理**: `tmux` の作業セッションを一覧化して復帰しやすくする
- **ログ管理**: コマンド実行単位のログを残して、あとから確認しやすくする
- **日本語で命令して、AI 側で英語に整理し、返答は日本語に戻す** という流れを作る

# 実装上の工夫
## 1. Azure Functions の API を固めた

現状の Chronicle API は次のルートを使う。

- `GET /api/health`
- `GET /api/sessions`
- `GET /api/session/get`
- `POST /api/session/update`
- `GET /api/logs`
- `POST /api/log/append`
- `POST /api/logs/backfill_nlp`
- `POST /api/nlp/analyze`

これで、セッション一覧・詳細・ログ・前処理までをひと通り扱える。

- 実装ファイル:
  api/chronicle-functions-python/function_app.py（スキーマ:
  chronicle_models.py、保存: chronicle_storage.py）
  
- GET /api/health
   説明: 稼働・ストレージ種別確認。
   レスポンス例:{"ok":true,"storage":"file"|"cosmos","timestamp":...}
   
- GET /api/sessions
   説明: 登録済セッション一覧。
   レスポンス: {"items":[...session objects...]}
   
- GET /api/session/get?server_id=<>&session_id=<>
   説明: 指定セッション詳細取得。
   レスポンス: {"ok":true,"item":{...}}
   必須クエリ: server_id, session_id
   
- POST /api/session/update
   説明: セッション登録／更新。
   Body: SessionUpdate {server_id, session_id,directory?, panes:list, updated_at?}
   レスポンス: {"ok":true,"item": saved_record}
   
- GET /api/logs?server_id=<>&session_id=<>&limit?=&since?=&until?=&topic?
   説明: 指定セッションのログ取得。
   レスポンス: {"ok":true,"items":[...log records...]}

- GET /api/logs/recent?limit?=&topic?
   説明: 全セッションからの最近ログ取得（topic で絞れる）

- POST /api/logs/backfill_nlp
   説明: 既存ログの NLP（analyze）を後付け。
   Body: {limit?:int, topic?:str,dry_run?:bool}
   動作: 未 NLP ログを取得→analyze_commandで注釈→（dry_run でないなら）保存

- POST /api/log/append
   説明: ログ追記（クライアントが使う主要エンドポイント）。
   Body: LogAppend{server_id, session_id, timestamp? , log, topic?, command?, exit_code?, cwd?}
   注: 環境変数 CHRONICLE_ANNOTATE_LOGS が真なら自動で NLPを付加して保存。
   レスポンス: {"ok":true,"item": saved_record}
   
- POST /api/nlp/analyze
   説明: 日本語などのテキストを解析して intent/entities → 英語プロンプト →
  final_prompt を返す。
  Body: {"text":"..."}
  レスポンス: {"ok":true,"nlp":..., "english_prompt": "...","final_prompt":"..."}
   必須クエリ: server_id, session_id
   
- GET /api/artifacts
   説明: アーティファクト一覧（現状プレースホルダ）。
   レスポンス: {"items":[...]}

## 2.　`ctm` は単なる tmux ラッパーではなく、Chronicle 操作の入口にした。

```bash
cd ~/Workspace/climax
./clients/setup_clients_env.sh
```

この1回で次が揃う。

- `clients/.env` を作る
- `CLIMAX_FUNCTIONS_URL` と `CLIMAX_FUNCTIONS_CODE` を入れる
- `ctm` / `ctmcmd` / `cj` / `climax-*` を PATH で使えるようにする


## 3. `ctm init <name>` で新規作成を1本化した

利用者が Cosmos や保存先を知らなくていいように、`ctm init` で次をまとめて実行する。

- `~/Workspace/<name>` を作る
- `codex-<name>` / `cmd-<name>` / `log-<name>` を作る
- 可能なら Chronicle に同期する
- `codex-<name>` に attach する

## 4. `ctm status` は session + logs を一緒に見せる

`status` は単に JSON を返すのではなく、次を同時に見せる。

- `session/get` の結果
- `logs` の直近結果
- `directory` と `panes` の意味

## 5. `ctmcmd` でコマンド単位ログを送る

`cmd-<name>` セッション内では `ctmcmd` を使う。

- `echo hello` のような単位で送る
- `topic` で `build` / `test` / `deploy` などに分類する
- 後で一覧や要約に使える

## 6. 管理画面を GitHub Pages に置いた
管理画面はAzureの認証で作成したが、コンテストに出すためだけに認証を削除してgithub pageで管理画面を用意した。
- **GitHub Pages 版**: Function Key を知っている人がすぐ使える
- **Azure Static Web Apps 版**: 将来的な認証付き運用に寄せやすい
- どちらの UI も、裏では Azure Functions の HTTP API を呼ぶ

GitHub Pages の管理画面では、

- `API base`
- `Function code`
- `server_id`

だけを入れればよい。

管理画面は Cosmos DB を直接読まない。ブラウザは Azure Functions の HTTP API を叩くだけで、実データの読み書きは Functions 側が Cosmos DB に対して行う。
Function code はブラウザの `localStorage` に保存し、サーバには残さない。

## 7. プロンプトの工夫
https://zenn.dev/oosawak/articles/climax-chronicle-preprocessor-ops

Climax では、**日本語で命令して、AI 側で英語に整理し、返答は日本語に戻す** という流れを採っている。

```text
日本語の入力
  ↓
Azure AI Language で intent / entities を抽出
  ↓
英語の task prompt を生成
  ↓
LLM 用の final prompt にする
  ↓
「返答は必ず日本語」を強制
```

## 具体的な狙い

- 音声入力や自然な日本語のまま命令できる
- AI の内部処理は英語の方が安定しやすい
- 返答は日本語のままにして、利用者の体験を崩さない

## 例

```text
日本語: 昨日の続きやって
↓
intent: continue_previous_task
↓
English prompt: Continue the previous development work from the latest context.
↓
final prompt: You must understand the task in English, but your final answer MUST be in Japanese.
```

この層分けがあると、

- 前処理の変更
- LLM の差し替え
- セッション管理ロジックの拡張

を独立して進めやすい。
こちらの機能は functions APIを作成しているが、今回提出してるものには含めていいない。githubのレポジトリーには処理を含めている。
