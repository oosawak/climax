# はじめに

AI の話をするなら、いきなり「コードをAIに書かせる話」から入るより、**先に仕様書を作る流れ** を共有した方が伝わりやすい。

周りのAI の使い方をしてると以下のように様々である。

①　Google 検索と同様に質問をして教えてもらった内容をプログラミングツールに入力して実装していく。
　以前は本で調べてプログラミングをしてた。それそれがインターネットでググれるようになり。現在はインターネットを検索する。よりもAIに聞いた方が早く情報が取得できます。

② プログラミングをしてくれるAIに、日本語のプロンプトを入力することにより、AI がプログラムを作ってくれる。

③　プログラミングツールに AI の機能は統合されており、そちらで使い方を聞いたり、プログラミングをしてもらったりする。


今回は、チャットAIをそのまま“実装AI”として使うのではなく、まずはスマホ上で仕様書や使用書を作る役に使う、ということだ。

流れはシンプルである。

1. スマホ上の ChatGPT、Gemini、Copilot で、まず仕様書を作る
2. 人間がその仕様書を確認する
3. Codex や CLI ベースの AI に渡して実装する
4. 実装に必要な README、サンプル、テスト、設定例も AI で用意する

この記事は、この流れを説明するためのまとめである。

## まずスマホで仕様書を作る

最初の役割は、スマホ上のチャットAIである。

ここでは、コードを直接書かせるのではなく、**何を作るのかを文章にする**。

たとえば、次のようなことを整理する。

- 何を作りたいのか
- 何を作らないのか
- 入力は何か
- 出力は何か
- どんな制約があるか
- 完成したと判断する条件は何か

この段階で使うのは、ChatGPT、Gemini、Copilot のような会話型のAIでよい。  
スマホから短く指示して、まずは仕様の下書きを作る。

ここでの目的は、**いきなりプログラムに飛ばず、先に考えを整理すること** である。

## 仕様書を人間が確認する

AI が作った仕様書は、そのまま実装に渡さない。

必ず人間が見て、次を確認する。

- 内容が正しいか
- 抜けている条件はないか
- 誤解を招く表現はないか
- 現場で実際に使えるか

この確認がないと、AI はそれっぽい文章を作れてしまうので、後で手戻りが増える。

大事なのは、**AI の出力を信じ切ることではなく、AI が整理したものを人間が判断すること** である。

## 実装は Codex や CLI ベースの AI に渡す

仕様書が固まったら、次は実装の段階になる。

ここで使うのは、Codex のようなプログラミング向け AI や、CLI ベースで動く実装支援 AI である。

この段階では、先ほど作った仕様書を入力にして、実際のコードを作らせる。

- アプリケーションの本体コード
- テストコード
- 修正案
- リファクタリング案

仕様が先に固まっているので、実装AIは迷いにくくなる。  
つまり、**チャットAIは仕様書を作る役、Codex や CLI AI は実装する役** と分けるのがポイントである。

## 実装に必要なリソースも AI で作る

AI の使いどころは、コード本体だけではない。

実装を進めるときに必要な周辺リソースも、AI で作れる。

- README
- サンプルコード
- テストデータ
- 設定例
- 手順書
- 初学者向けの説明文

これらを先に整えると、コードだけでなく、**実際に使える状態** に近づく。

特に教育現場では、プログラムそのものよりも、説明や手順のわかりやすさが重要になることが多い。  
だからこそ、周辺リソースを AI で作る価値は大きい。

## このやり方の良さ

この流れの利点は、いきなり実装に入らないことにある。

### 1. 手戻りが減る

先に仕様を固めるので、実装後に「そもそも違った」が起きにくい。

### 2. 役割分担が明確になる

- チャットAI: 仕様書を作る
- 人間: 仕様を確認する
- Codex / CLI AI: 実装する
- AI: リソースも補う

この分担が見えると、AI をどこで使うべきか説明しやすい。

### 3. 教育現場でも使いやすい

授業や演習では、いきなり完成コードを見せるより、仕様から実装までの流れを見せた方が理解されやすい。

学生にも「まず文章で考える」「次に確認する」「最後に実装する」という順番を伝えやすい。

### Githubを有効に使う。
私がプロジェクトを作る手順は、
① プロジェクトホルダーを作る。
② githubレポジトリーを作る。
③ git clone でプロジェクトホルダーにレポジトリーを割り当てる。
④ プロジェクトに更新があればコミットしてプッシュ。
⑤ github pageを利用してデバッグをしたり、生産物を公開する。
　ローカルホストで確認をしてもいいが、設定が面倒なこともあり、Web 系に収まるようなものはgithub pageを利用している。

## まとめ

今回の考え方は、AI を一つの道具として雑にまとめるのではなく、役割ごとに分けて使うことである。

- チャットAIで仕様書を作る
- 人間が仕様を確認する
- 実装AIでプログラムを作る
- 必要なリソースも AI で作る

この順番にすると、AI を使った開発がかなり整理される。
