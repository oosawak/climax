# はじめに

木曜日に同僚へ AI の話をするなら、単なる「すごい技術紹介」よりも、**現場でどう使うか** を軸にした方が伝わりやすい。

特に最近よく出てくる「バイブコーディング」は、雰囲気で雑に書くという意味ではない。  
実際には、**人が意図を言語化し、AI に下書きを作らせ、最後は人が責任を持って確認する** という作業スタイルに近い。

この記事は、専門学校の先生や同僚に向けて、

- AI に何を任せると良いか
- どこは人間が見るべきか
- 授業や実務でどう使うと安全か

を、できるだけ実践寄りに整理したメモである。

## バイブコーディングとは何か

バイブコーディングを一言でいうと、**コードを書く前に、まず意図を AI に渡す開発スタイル** である。

たとえば、いきなりファイルを手で作るのではなく、先にこう伝える。

- 何を作りたいのか
- どんな入力を受けるのか
- どんな出力が欲しいのか
- どこまで自動で、どこから手作業か

AI はここから、たたき台のコード、テスト、説明文、リファクタ案を出せる。  
人間はそれを見て、筋が悪いところを直し、完成まで持っていく。

このやり方の価値は、**「考える時間」を減らすことではなく、「最初の形を作る時間」を圧縮すること** にある。

## AI に向いている仕事

AI は万能ではないが、得意な仕事はかなりはっきりしている。

### 1. たたき台を作る

ゼロから完璧な実装を狙うより、まずは動くものを出させた方が速い。

たとえば次のような作業は相性が良い。

- CRUD のひな形を作る
- API の型定義を出す
- 入力チェックの基本形を書く
- README や手順書のドラフトを作る

### 2. 既存コードの要約

授業や引き継ぎで意外に効くのが、既存コードの読み解きである。

- この関数は何をしているか
- この分岐は何のためか
- この API はどの順で呼ばれるか

といった説明を AI にさせると、理解の初速が上がる。

### 3. テストや例外処理の補助

AI は「抜けやすいところ」を指摘するのが得意だ。

- null や空文字の扱い
- 想定外の型
- 例外処理の不足
- 境界値テストの不足

人が見落としやすい部分の確認役として使うと価値が出る。

## AI に任せすぎない方がいい仕事

逆に、AI をそのまま信じると事故りやすい領域もある。

### 1. 要件が曖昧なままの実装

「いい感じにして」は危険である。  
AI は穴を埋めるのが上手いので、曖昧な指示でもそれっぽく完成させてしまう。

しかし、完成したように見えて、実際の要件とズレていることがある。

### 2. セキュリティや権限まわり

認証、認可、秘密情報、外部 API キー、ファイルアクセスは人間が必ず確認したい。

AI は安全そうな雰囲気のコードを出しても、実運用の基準を満たしていないことがある。

### 3. 採点や評価の最終判断

教育現場では、AI を使って課題やレポートの下書きを作ることはある。  
ただし、最終的な評価や合否判断を AI に寄せるのは危ない。

AI は補助者であって、責任主体にはできない。

## 同僚に伝えるときの説明の軸

同僚に AI を紹介するときは、機能名よりも、**既存の仕事がどう変わるか** で話すと伝わる。

### 1. 「置き換え」より「前倒し」

AI は先生の仕事を全部奪うものではない。  
むしろ、

- 準備
- たたき台作成
- 例示
- 反復修正

を前倒ししてくれる道具と考えた方が現実的である。

### 2. 「正解を出す機械」より「壁打ち相手」

授業準備では、AI を「答えを出す人」ではなく「壁打ち相手」にすると使いやすい。

- この説明は初学者に通じるか
- 別の例えはないか
- 課題文が曖昧ではないか

こういう確認に向いている。

### 3. 「速さ」だけでなく「再現性」

AI の価値は速さだけではない。

同じ型で何度も使えること、別の授業にも流用できること、説明の粒度を揃えられることが大きい。

## 授業や業務で使うときの型

実際には、次の5段階にすると安定する。

### 1. 目的を1文で書く

まず、やりたいことを短く言う。

例:

- 「Python で CSV を読み込み、集計するサンプルを作りたい」
- 「Web アプリのログイン画面の雛形を作りたい」
- 「学生向けに API の概念を説明する教材を作りたい」

### 2. 制約を書く

次に、外してほしくない条件を書く。

- 初学者向け
- できるだけ短いコード
- 外部ライブラリは最小限
- Windows でも動く
- 授業時間は 15 分

制約があるほど、AI の出力は現場向きになる。

### 3. まず下書きを出させる

最初から完成版を狙わない。

まずは、

- 構成案
- サンプルコード
- 手順の見出し
- 想定質問

を出させる。

### 4. 人間がレビューする

ここが本番である。

- 間違った前提がないか
- 難しすぎないか
- 学生に誤解を与えないか
- 実際に動くか

この確認を飛ばすと、AI 利用は一気に危うくなる。

### 5. 授業や実務に合わせて整える

AI が出したものを、そのまま使うのではなく、現場の言葉に直す。

専門学校なら特に、

- 初学者がつまずく箇所
- 実習時間の長さ
- 評価観点
- 配布資料の形式

に合わせる必要がある。

## Thursday 用の話し方の例

木曜日に話すなら、最初の一言はこういう形がよい。

> AI は「答えを出してくれる機械」ではなく、「準備と反復を速くする道具」です。  
> だから授業や実務では、AI に全部任せるより、先生が設計して AI に下書きを作らせる方がうまくいきます。

この説明なら、過度に煽らず、実務の話として受け取ってもらいやすい。

## 30分で見せるなら何をやるか

短いデモなら、次の順番が分かりやすい。

1. 仕様を1文で書く
2. AI にコードの下書きを作らせる
3. 生成されたコードを人間が読む
4. バグや不足を 1 つ直す
5. どう改善したかを説明する

この流れを見ると、AI は魔法ではなく、**高速な共同作業者** だと伝わる。

## まとめ

AI 時代のバイブコーディングで大事なのは、派手なデモではなく、**人間の役割を先に決めること** である。

- AI は下書きと反復を速くする
- 人間は要件、判断、責任を持つ
- 教育現場では、説明の再現性を上げる道具として使う

この視点で話すと、同僚に対しても「AI を使うべきか」ではなく、「どう使うと安全で役に立つか」という会話に持ち込みやすい。

木曜日の説明資料として使うなら、まずはこの 3 点だけ押さえれば十分だ。

- AI に何を任せるか
- どこを人間が見るか
- 現場の制約をどう書くか
